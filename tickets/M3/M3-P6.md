# Make the per-home scoring rebuild take minutes, not 40+

## Why this ticket exists (the story)

Rebuilding `core.mv_home_signals`, one row per gated home with every score input, took
**~10 min for Travis alone** (217k homes). It took **~42 min** once Harris (836k parcels) and
Williamson (158k) were added. On 2026-09-26 that rebuild also:

- timed out twice (25 min and 90 min statement timeouts);
- failed once with `DiskFull: could not write to file base/pgsql_tmp/...: No space left on device`,
  after **50 GB** of cumulative temp-file spill with `work_mem = 5MB`;
- held up the M3/M4 release by hours.

Every later change to the scoring inputs pays this cost again. This ticket makes a full
three-county rebuild take **a few minutes** and keeps it there as counties are added.

## What we measured (don't guess, measure)

These were micro-benchmarks on the live Supabase instance (Small compute, PostGIS 3.3.7,
GEOS 3.14), using a 5,000-home sample from Harris and Travis. The projection to 1.2M homes
is linear (×240). The costs are for work the build does **once per home, on every rebuild**:

| Component | 5,000 homes | Projected for 1.2M homes | Notes |
|---|---|---|---|
| FEMA flood-zone point-in-polygon (raw polygons) | **3.71 s** | **~15 min** | The single biggest cost |
| Same, after `ST_Subdivide(geom, 256)` | 0.37 s | ~1.5 min | **10× faster**, identical result (312 hits in both) |
| Block-group point-in-polygon | 0.47 s | ~2 min | Already small polygons |
| Utility-territory point-in-polygon | 0.28 s | ~70 s | Subdividing gave only 1.6× (see below) |
| Own-permit lookups (`permits.tcad_id = parcels.geo_id`) | 0.29 s | ~70 s | Indexed btree, fine |
| `ST_PointOnSurface` of the parcel polygon | 0.09 s | ~20 s | Fine |

**What remains after spatial (~20 min):** sort and array work in the view definition.
- **Six `percent_rank()` window functions** over ~1.2M rows each. These are the legacy
  `*_pctile` columns, kept only for backward compatibility; scoring has used anchored terms
  since M2-P8.
- **Per-home `array_agg(distinct …)` / `unnest` source lists.** Each home carries a
  `uuid[]` of source-manifest ids built by union and de-duplication.
- **A `DISTINCT ON (prop_id)`** to pick one territory per home.
- **Six `percentile_cont` anchor computations.** These are small, since each is one pass.

Polygon complexity measured in the database:

| Layer | Polygons | Avg vertices | Max vertices | Bounding box vs real area |
|---|---|---|---|---|
| `core.flood_zones` (FEMA NFHL) | 5,775 | 592 | **311,377** | worst polygon: bbox 426 km², real area **22 km²** (19× larger box) |
| `core.territories` (HIFLD) | 141 | 5,593 | 51,951 | Oncor: bbox 936,546 km² vs area 214,050 km² |
| `core.block_groups` (TIGER) | 18,638 | 267 | 13,724 | compact |

## The theory: why a spatial index doesn't save you here

**How a point-in-polygon query runs in PostGIS.** `ST_Within(point, polygon)` with a GiST
index happens in two stages:

1. **Index filter (cheap).** The GiST index is an R-tree of **bounding boxes**. It returns
   every polygon whose *box* contains the point, in microseconds.
2. **Exact test (expensive).** For each candidate, GEOS runs the real point-in-polygon test
   (ray casting / winding number). Its cost is **O(number of vertices)** of that polygon.
   Unless a prepared-geometry cache is hit, it walks every edge.

So the index only helps if bounding boxes are **small and specific**.
- **A flood zone** that is a long, thin river corridor has a box 19× its real area. Thousands
  of homes fall inside that box but outside the actual zone, and every one of them pays a
  **311,377-vertex** exact test.
- **A utility territory** covering a third of Texas has a box containing *every* home in
  the county. The index filters out nothing.

**Why `ST_Subdivide` works.** `ST_Subdivide(geom, 256)` cuts a polygon recursively into
pieces of at most 256 vertices each. Every piece has a *tight* bounding box.
- The index now returns 0–2 tiny candidates per home instead of one giant polygon.
- The exact test is ≤ 256 vertices instead of 311,377.

That's the 10× on flood zones. Territories gained only 1.6×, because the HIFLD territories
overlap so heavily that every home is inside several of them anyway (see M3's utility-gate
decision). The exact tests there pass, and passing is cheap.

**Why caching beats both.** A home's block group, flood-zone membership and territory
candidates depend only on:
- the parcel geometry (changes only when the appraisal roll is re-downloaded);
- static boundary files (TIGER 2024, FEMA NFHL snapshot, HIFLD snapshot, City of Austin
  service area).

Recomputing them on every score refresh is wasted work. Compute them **once per
(home, source-file version)** into `core.home_spatial`, and recompute only homes whose parcel
or source file changed (the SHA-256s are already in `ops.source_manifest`). The scoring view
then joins by `prop_id`, with **zero geometry at refresh time**.

**Why the sorts spilled to disk.** A `percent_rank()` over 1.2M rows sorts 1.2M rows. With
`work_mem = 5MB` (Supabase's default for our role), each sort that exceeds 5 MB becomes an
*external merge sort* writing temp files under `base/pgsql_tmp`. Six of them, plus the
array de-duplication, over a 45-minute run wrote **50 GB** of temp files on a small disk.
- Raising `work_mem` to 256 MB for the build session fixed the spill, but it treats the
  symptom.
- Deleting the six legacy sorts removes the cause.

## What to build

1. **`core.flood_zones_sub` and `core.territories_sub`**: subdivided copies, rebuilt only
   when their source file changes.
   ```sql
   create table core.flood_zones_sub as
     select f.id as flood_zone_id, f.fld_zone, f.sfha, f.source_id,
            extensions.ST_Subdivide(f.geom, 256) as geom
     from core.flood_zones f;
   create index flood_zones_sub_gix on core.flood_zones_sub using gist (geom);
   analyze core.flood_zones_sub;
   -- same for core.territories (+ the City of Austin override polygon)
   ```
   Keep the originals for display and provenance. Only lookups use the `_sub` tables.

2. **`core.home_spatial`**, one row per parcel with a geometry:
   ```
   prop_id pk, county_fips, pt (geometry point, from centroid or ST_PointOnSurface),
   block_group_geoid, in_sfha boolean (null + reason when that county has no flood data loaded),
   territory_candidates text[] (all eia_ids containing pt), resolved_territory_eia_id,
   territory_basis ('service_area_polygon' | 'most_likely_county_utility' | null),
   territory_null_reason, parcel_source_id, boundary_source_ids uuid[], computed_at
   ```
   - **Populate with a loader, not a view:** `pipelines/sources/home_spatial.py`.
   - **Incremental.** Recompute only homes whose `parcel_source_id` changed, or all homes when
     a boundary file's manifest id changes.
   - **Bulk load.** Batched `COPY` into a staging table plus an upsert (repo rule), one
     county at a time.

3. **Rewrite `core.mv_home_signals`** to read `core.home_spatial` by `prop_id` instead of
   running `ST_Within` / `ST_Intersects`. Use build-beside + swap (see lessons).
   - **Delete the six legacy `*_pctile` columns.** Check first that nothing in `web/`, `api.*`
     or `pipelines/` still reads them (`grep -rn "_pctile"`), keep a deprecation alias if
     something does, and remove it in a later ticket.
   - **Build per-home `source_ids` once in `home_spatial` / loaders,** not with
     `array_agg(distinct …)` over unnested arrays at refresh time.

4. **Benchmark before and after**, recorded in `checks/M3-P6.md` with the method:
   - full `core.refresh_all_scores()` wall-clock (before: ~2,548 s on 2026-09-26);
   - `temp_bytes` delta from `pg_stat_database` across the refresh;
   - peak `pg_database_size`;
   - `EXPLAIN (ANALYZE, BUFFERS)` of the old and new definitions on one county.

## Acceptance criteria

- [ ] **Speed.** A full `core.refresh_all_scores()` for Travis + Harris + Williamson finishes
      in **≤ 5 minutes** with `work_mem` at its default (no session override), measured and
      recorded in `checks/M3-P6.md`.
- [ ] **No spill.** The temp-file bytes written during that refresh are **< 1 GB**.
- [ ] **Same results.**
  - `core.mv_home_signals` rows are identical before and after for every column that still
    exists: row-by-row `except` both ways on a 50k-home sample per county, plus exact
    per-county gate counts.
  - Flood membership is identical: raw vs subdivided agrees for 100% of homes (subdivision
    must not change answers).
- [ ] **Incremental.** Re-running `home_spatial` with no changed sources touches 0 rows and
      finishes in seconds.
- [ ] **Indexes survive the swap.** Every index on the swapped views is re-created in the
      migration (list them).
- [ ] **No web regression.** All web tests pass, and `/ranking` is < 1.5 s for Travis and Harris.

## Lessons this project learned the hard way (read before touching the database)

1. **Measure before you theorize.** The first guess was "utility territories are the
   bottleneck (51k-vertex polygons)". The benchmark said territories cost ~70 s and **flood
   zones cost ~15 min**. Subdividing territories alone would have wasted a day. Measure a
   5,000-row sample of each component first.
2. **Spatial indexes filter by bounding box, not by shape.** Long, thin or huge polygons
   defeat them. Subdivide anything with thousands of vertices or a sprawling footprint.
3. **Don't recompute static facts on every refresh.** If an input only changes when a
   source file changes, cache the answer keyed by that file's manifest id.
4. **One giant transaction multiplies retry cost.** P8a and the 0303 build each failed
   *after* 5–40 minutes of work and rolled everything back. Commit expensive steps on their
   own (build → commit → derive → commit), then do DDL swaps as a fast `BEGIN … ROLLBACK` dry
   run before the real one.
5. **Replacing a materialized view drops its indexes.** A rename-swap binds the name to a new
   object, so every index created ad hoc on the old one (for example `0208`'s county+territory
   index) is gone. Restate all indexes in the swap migration.
6. **Views and functions bind to objects, not names.** After a rename-swap, views still point
   at the *old* object. Drop and recreate dependents in the swap, then check that
   `pg_views` / `pg_proc` no longer mention `_old`.
7. **`create or replace function` with a different argument list makes an overload.** It
   doesn't replace. Two overloads with defaults make short calls fail with "function … is
   not unique". Drop the old signature explicitly.
8. **Generic plans turn `(param is null or col = param)` into a full scan.** Inside SQL
   functions, use `col = coalesce(param, default)` on indexed columns (fixed in `0218`:
   1.2M-row scan → county index).
9. **Never insert one row per statement over the network.** About 70 ms round-trip × 280k
   ERCOT rows ≈ 5 h. `COPY` into a staging table plus one upsert per batch took minutes.
10. **`work_mem` decides whether sorts stay in memory.** At 5 MB, every large sort spills to
    disk. Temp files count against the same disk as data, so a big build can fill it and
    flip Supabase read-only (the "read-only blips" seen during the Harris load).
11. **Bulk rewrites leave dead rows.** Three full re-scores left `home_propensity` at 1.5 GB;
    `VACUUM FULL` brought it to 750 MB. Autovacuum's analyze trigger (10% changed) also missed
    `parcel_geoms` at 7.5%, so run `vacuum (analyze)` explicitly after big loads.
12. **Coarse public boundaries overlap.** HIFLD territories put every Harris home inside
    CenterPoint, Entergy *and* San Bernard polygons. Check for overlaps before trusting a
    point-in-polygon answer as "the" utility.
