## Course correction (coordinator, mid-ticket)

The first draft of this ticket's apply order said "confirm 0303 +
0303b applied first." That was wrong: 0303/0303b (uncommitted, in a
different worktree) build `core.mv_home_signals_v2` with **live**
`ST_Within` against `core.territories` (full-size, un-subdivided) —
that build is itself the 25–35+ minute step that already hit
OOM/disk-full on 2026-09-26. Forcing it to run before this ticket's
optimization would defeat the point.

**Fixed:** 0304/0304b no longer depend on 0303/0303b at all. They build
directly against the CURRENT live schema (verified via `pg_catalog`
above). The apply path below never runs 0303's heavy build. Do not
apply 0303/0303b on this path — they are superseded by 0304/0304b, which
carries every semantic they intended (territory_basis, county-aware gate
counts, `mv_home_terms`, `mv_home_geo_rollup`, `api.loaded_counties`,
`mv_county_territories`, the function-overload drops, the city/zip
filter form, view rebinding, restated indexes) without the live-geometry
build.

Also fixed per the same review: `core.home_permit_agg`'s per-home
`array_agg(distinct pm.source_id) filter (...)` (one of the two
remaining >5-min costs alongside the six `percent_rank()`s) is now a
plain `array_agg(pm.source_id) filter (...)` — the inner per-home
`DISTINCT` was redundant with `raw`'s own single final
`array(select distinct ...)`, which already dedups every source id
(static + dynamic) once per home. The other `array_agg(distinct ...)`
sites in `0304b_spatial_precompute_swap.sql` (`bg_permit_counts`,
`county_proxy`, `mv_gate_counts`/`mv_gate_counts_by_market`'s `srcs`
CTEs) are all small aggregates grouped by block group/county/reason (at
most a few dozen output rows), not per-home, and are left as-is — they
are not the cost class this ticket targets.

## Apply order (once DB-write is approved)

1. `supabase/migrations/0304_spatial_precompute.sql` — DDL only
   (`core.flood_zones_sub`, `core.territories_sub`, `core.home_spatial`).
   No live consumer reads any of these three yet, so this step is
   inert with respect to the running app. Est. ~1–2 min
   (`core.flood_zones_sub` subdivides 5,775 polygons;
   `core.territories_sub` subdivides 141 — both trivial; table + index
   creation is instant).
2. `python -m pipelines.run home_spatial --backfill` — the registry
   entrypoint (`pipelines/sources/home_spatial.py:run()`) loops every
   county already in `core.parcels` (Travis 48453 ~442k parcels, Harris
   48201 ~836k, Williamson 48491 ~158k), each one its own committed batch
   sequence via `run_county()` (lesson 4), 20k rows/batch
   (`BATCH_SIZE`). For a single county in isolation (e.g. re-running just
   Harris after a boundary-file update), call
   `home_spatial.run_county(county_fips="48201", runner="cli",
   backfill=True)` directly. Projected from the ticket's own 5,000-home
   micro-benchmarks (flood 0.37s, block-group 0.47s, territory 0.28s
   subdivided, ×240 to 1.2M, split across three counties): **Travis
   ~25s, Harris ~50s, Williamson ~10s** of pure spatial-match time;
   wall-clock will run longer once COPY/upsert round-trips are included
   — budget **a few minutes per county**, well under any single-step
   limit. `core.home_spatial` is a brand-new table with no live reader
   yet, so this step is also inert with respect to the running app.
3. `supabase/migrations/0304b_spatial_precompute_swap.sql` — the ONE
   swap. Builds `core.mv_home_signals` fresh (build-beside as
   `mv_home_signals_v2`, then rename-swap) as a pure ID join onto
   `core.home_spatial` — zero `ST_Within`/`ST_Intersects`, no
   `percent_rank()` — then rebuilds every matview/api view/function that
   reads it (lesson 6). Est. **well under 1 min** at 1.2M rows: the only
   non-trivial per-home work left is the `LEFT JOIN core.permits` in
   `home_permit_agg` and the small final source-id dedup, both O(n) hash
   joins, not sorts.
4. Outside the transaction: `vacuum (analyze)` on
   `core.mv_home_signals_pre_m3p6`, `core.home_spatial`,
   `core.home_propensity` (lesson 11).
5. `select core.refresh_all_scores();` for the real post-cutover
   wall-clock measurement below.

## Known risks / follow-ups carried forward (not fixed here — out of this ticket's `owns`)

1. **Deprecated `*_pctile` columns.** `grep -rn "_pctile" web/ supabase/
   pipelines/` found two consumers outside `supabase/migrations/`
   (historical migrations don't matter):
   - `web/tests/m2-map/homes-ranked-weighted.test.ts` (lines ~109-111)
   - `web/tests/m2/top-homes-route.test.ts` (lines ~41-43, ~66-67)

   Both query `distributor_saidi_pctile` / `flood_pctile` /
   `empower_pctile` / `acs_65_pctile` / `acs_heat_pctile` /
   `backup_intent_pctile` directly against `core.mv_home_signals`, and one
   asserts `count(distinct acs_65_pctile) > 1` (real percentile
   variance). `0304b` keeps these six columns (so the tests don't hit an
   unknown-column error) but sets them to `null` always — the
   `percent_rank()` computation that produced real values is exactly the
   cost this ticket removes. **These two tests will fail** once `0304b`
   is live; per the ticket's own instruction ("keep a deprecation alias
   if something [still reads them], and remove it in a later ticket"),
   flagged here as follow-up, not fixed in this ticket (`web/` paths are
   outside `owns`). `api.home_score_breakdown` also reads these columns
   for its `percentile` display field; it needs no code change — it will
   simply display `null` percentile for those five signals (a
   display-only regression; scoring itself is anchored-absolute, never
   percentile, per M2-P8).
2. **Per-home permit source ids.** `home_permit_agg`'s
   `array_agg(pm.source_id) filter (...)` is still a per-home aggregate
   over a `LEFT JOIN core.permits` (1.2M rows). The real fix — a
   precomputed per-home permit-source table maintained by the permits
   pipeline itself — is out of this ticket's owns paths (`pipelines/
   sources/home_spatial.py` is spatial data only, not permits). Residual
   cost is expected to be small (a hash join + trivial per-row array,
   not a sort) but is not separately benchmarked here.
3. **`core.mv_home_block_group`.** Its own refresh (called first in
   `core.refresh_all_scores()`) still does live `ST_Within` (block-group
   point-in-polygon, ~2 min projected at 1.2M homes) for whatever other
   consumers still read it (0102/0201/0213 per
   `grep -rl mv_home_block_group supabase/migrations/`). `mv_home_signals`
   no longer needs it (home_spatial has its own `block_group_geoid`).
   Retiring it outright requires checking every consumer — a follow-up
   ticket, not done here to avoid breaking something outside this
   ticket's visibility.
