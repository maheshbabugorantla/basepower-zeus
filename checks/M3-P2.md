## State class mapping (single-family gate)

Harris uses the **same Texas PTAD state class codes** Travis (TCAD) does
(verified live against `desc_r_01_state_class.txt`):

```
A1	A1  	Real, Residential, Single-Family
```

— byte-identical description text to TCAD's own layout. Gate:
`imprv_state_cd` or `land_state_cd` starts with `A1`, exactly as
migration `0101_m1.sql` already documents for Travis. HCAD's
`real_acct.txt` has one unified `state_class` column (not TCAD's split
improvement/land columns), so `hcad_parcels.py` writes the same value
into both `core.parcels.imprv_state_cd` and `.land_state_cd`.

## Homestead mapping

HCAD's `real_acct.txt` carries no direct homestead flag column (unlike
TCAD's PROP.TXT, which has `hs_exempt` inline). The homestead flag comes
from a join against `jur_exempt_cd.txt`'s per-account exemption category
token list: `desc_r_14_exemption_category.txt` (inside
`Code_description_real.zip`) confirms `RES` = "Residential Homestead".
`build_homestead_set()` in `hcad_parcels.py` streams `jur_exempt_cd.txt`
once and keeps every `acct` whose `exempt_cat` field contains the `RES`
token (space-separated list, e.g. `HIS RES` still counts). Verified live
count against the full file: **871,646** Harris accounts carry the `RES`
token.

## Geometry source: the "Shapefiles" download was actually a File Geodatabase

The GIS downloads API's `Parcels.zip` entry (listed under category `GIS`
/ subcategory `Shapefiles`, filename `Parcels.zip`, "Contains parcel
polygons and HCAD account number of real property") was downloaded
(210,188,453 bytes) and inspected — it is an **Esri File Geodatabase**
(`Parcels/Parcels.gdb/*.gdbtable` etc.), not an ESRI Shapefile, despite
the API's category label. This repo's `pipelines/requirements.txt` has
`pyshp` (a `.shp`/`.dbf` reader) but no File Geodatabase reader (`gdal`/
`fiona`/`pyogrio`), and this ticket cannot add one (only
`pipelines/config/counties.yaml`, `pipelines/sources/hcad_parcels.py`,
its test, and its fixtures are `owns`). `Parcels.zip` was deleted after
this was discovered (never got an `ops.source_manifest` row — an
unusable, unloaded file has no place staying in `data/raw/hcad/`).

Replacement: HCAD's own public ArcGIS REST feature layer
`https://www.gis.hctx.net/arcgis/rest/services/HCAD/Parcels/MapServer/0`
serves the identical parcel polygons plus `HCAD_NUM`/`acct_num`/
`state_class` attributes directly as GeoJSON over plain HTTPS — the same
kind of source Travis's own `tcad_geometry.py` already uses for its
county GIS layer (`checks/T0-H3.md`). `hcad_parcels.py` reimplements
that module's proven keyset-paging / RFC 8142 framing / TUS-upload
pattern (not imported, since this ticket owns only `hcad_parcels.py`),
server-side filtered to `state_class='A1'` (1,156,673 of 1,550,492
features), then locally filtered again to the same homestead set
`core.parcels` uses, so `core.parcel_geoms` carries geometry for exactly
the same Harris row set `core.parcels` does.

Join key: `HCAD_NUM` on the geometry layer == `acct` in `real_acct.txt`
== the account number HCAD's PDATA downloads and its GIS layer both use
natively as a 13-character, left-zero-padded string (verified live:
`HCAD_NUM == acct_num == '0440300000049'` for a real feature) — kept
as-is in `core.parcels.prop_id`/`core.parcel_geoms.prop_id`, unlike
Travis's TCAD `prop_id` which is normalized by stripping leading zeros
(Travis's own join key needs that; Harris's geometry layer's native key
is already the zero-padded form, so stripping zeros would be the wrong
transformation here, not a missing one).

## Load strategy (binding, from the ticket)

Single-family homesteads are filtered **before** loading (never a soft
filter applied later in a view): `hcad_parcels.py` streams
`jur_exempt_cd.txt` once into an in-memory homestead-account set
(871,646 accounts, well under 1M short strings), then streams
`real_acct.txt` once, keeping a row only if `state_class` starts `A1`
AND its `acct` is in that set. Batches are `COPY`ed into
`core.parcels`/`core.parcel_geoms` in chunks; before every chunk,
`_wait_for_refresh_clear()` polls `pg_stat_activity` for any other
session running a query matching `%refresh materialized view%` or
`%refresh_all_scores%` and sleeps (bounded, up to 10 minutes) until
clear. This module never refreshes any materialized view or calls any
scoring function itself.
