# M2-H3 — emPOWER access path decision

## Decision: **queryable ArcGIS REST FeatureServer** (no manual download needed)

HHS publishes emPOWER as a public, anonymous, no-key ArcGIS Feature Service. It is
queried directly by `pipelines/sources/empower.py` (M2-P4) with plain HTTPS GET
requests — no browser, no scraping, no manual file drop required.

## How it was found

- `https://empowerprogram.hhs.gov/about-empowermap.html` links to `empower-rest.html`
  and directly to the FeatureServer root:
  `https://services2.arcgis.com/ZQ4jTQn6k7VPXEwO/arcgis/rest/services/HHS_emPOWER_REST_Service_Public/FeatureServer`
- `https://empowerprogram.hhs.gov/empower-rest.html` confirms in plain text: "monthly
  updated de-identified total ... for Medicare beneficiaries" and "monthly updated
  total for the number of Medicare beneficiaries who have had an administrative
  claim for one or more types of electricity-dependent DME."
- No browser/JS inspection was needed — the endpoint is a documented, public,
  anonymous-access ArcGIS REST service (`capabilities: "Query,Extract"`,
  `allowAnonymousToQuery: true`), directly linked from HHS's own
  `about-empowermap.html` and `empower-rest.html` pages, and independently
  discoverable from its own ArcGIS Online item page
  (`https://www.arcgis.com/home/item.html?id=e6f7b3ebcec64edd9093664927d25b7d`).
  Whether `empowermap.hhs.gov`'s interactive map widget calls this exact
  FeatureServer internally, or a private mirror of it, was not verified (not
  needed for M2 — the public REST Service is HHS's documented, sanctioned path
  regardless).

## Endpoint

```
Base:   https://services2.arcgis.com/ZQ4jTQn6k7VPXEwO/arcgis/rest/services/HHS_emPOWER_REST_Service_Public/FeatureServer
Layer:  1  — "Electricity Dependent DME – ALL – ZipLevel" (esriGeometryPolygon)
```

Other layers on the same service (2=CountyLevel, 3=StateLevel of the same metric,
plus 5–23 = ESRD dialysis / O2 / home health / hospice / any-healthcare-service
variants at Zip/County/State level) exist but are not needed for M2.

Query used (proved working, small request, Travis County ZIPs):

```
GET {base}/1/query
  ?where=STATE='TX' AND Zip_Code IN ('78701','78702',...,'78759')
  &outFields=STATE,COUNTY,Zip_Code,Medicare_Benes,Power_Dependent_Devices_DME,Any_Healthcare_Srvc_Any_DME
  &returnGeometry=false
  &f=json
```
Returned HTTP 200, 41 features. A second query with
`where=STATE='TX' AND COUNTY='Harris'` also returned HTTP 200. `returnCountOnly=true`
row counts (2026-09-26):

| Filter | Row count |
|---|---|
| `STATE='TX' AND COUNTY='Harris'` | 130 |
| `STATE='TX' AND COUNTY='Travis'` | 50 |
| `STATE='TX'` (all TX ZIPs) | 1850 |

All three are under the `maxRecordCount` of 2000, so **no pagination is required**
even for a full-TX pull today (the earlier `exceededTransferLimit: true` seen while
inspecting Harris was caused by passing `resultRecordCount=5` in that test call, not
by the true row count exceeding 2000). Pagination via `resultOffset`/
`resultRecordCount` would still be needed if a query is scoped nationwide, or if TX's
row count grows past 2000 in the future — P4 should page defensively rather than
assume it will always fit in one page.

No API key or auth is required (`allowAnonymousToQuery: true`). `f=geojson` and
`f=json` (Esri JSON) are both supported; CSV/shapefile/etc. bulk export is also
listed (`supportedExportFormats`) if a one-shot table dump is ever preferred over
paged queries.

## Fields (layer 1)

| Field | Type | Meaning |
|---|---|---|
| STATE | string | 2-letter state/territory code |
| COUNTY | string | County name |
| PA_NAME | string | Postal area name |
| Zip_Code | string | ZIP code — the join key for `core.empower_zip`. In every TX row checked, `Zip_Code` equals `Zip_Code_Recode` (see Verification), so which field is the "current" vs. "parent" ZIP could not be distinguished from TX data alone; use `Zip_Code` since it holds the plain 5-digit ZIP (e.g. `78701`) |
| Zip_Code_Recode | string | Per HHS's docs, meant to hold the parent ZIP for non-boundary (e.g. PO Box) ZIPs, but was identical to `Zip_Code` for all TX rows queried — the parent-vs-child distinction likely only shows up for non-TX PO-Box ZIPs, not verified here |
| County_FIPS_Code, State_FIPS_Code, FIPS_Code | string | FIPS identifiers |
| Medicare_Benes | integer | **Total Medicare beneficiaries** in the ZIP (all enrollment types, FFS Parts A&B + Medicare Advantage Part C) |
| Power_Dependent_Devices_DME | integer | **Electricity-dependent Medicare beneficiaries** — count with a claim for electricity-dependent DME/cardiac devices (ventilators, BiPAP, O2 concentrator, enteral feeding pump, IV infusion pump, suction pump, at-home ESRD dialysis, motorized wheelchair/scooter, electric bed, LVAD/RVAD/BIVAD/TAH) |
| Facility_ESRD_Dialysis_Any_DME, O2_Services_Any_DME, Home_Health_Services_Any_DME, AtHome_Hospice_Any_DME, Any_Healthcare_Srvc_Any_DME | integer | Sub-breakdowns inferred from field/layer names only (facility dialysis, O2 services, home health, hospice, any of the above), not cross-checked against `HHSemPOWERMap_HistoricalDataset_Dictionary.xlsx` — treat these meanings as provisional; not required for M2 but available |
| AREA, Shape__Area, Shape__Length | double | Polygon geometry stats (irrelevant when `returnGeometry=false`) |

Only `Zip_Code`, `Medicare_Benes`, and `Power_Dependent_Devices_DME` are needed for
`core.empower_zip` per M2-P4's contract.

## Cadence / vintage

- Service description text and `empower-rest.html` both state the data is
  **updated monthly**. Neither that page nor the ArcGIS item metadata
  (`https://www.arcgis.com/sharing/rest/content/items/e6f7b3ebcec64edd9093664927d25b7d?f=json`
  — checked `snippet`, `description`, `tags`, `typeKeywords`) states the claims
  month directly; `editingInfo.lastEditDate` (epoch ms `1790019400896` =
  2026-09-21 19:36:40 UTC) is only when the *layer* was last edited, not the
  vintage of the data inside it.
- **Latest month confirmed by cross-check, not by a field on the service.**
  Downloaded `2026_HHSemPOWERMapHistoricalDataset.xlsx` (the yearly historical
  file HHS links from `about-empowermap.html`) into the main checkout's
  `data/raw/empower/` (see Verification below). Its `Zip Code` sheet has one
  column set per month (`Jan_2026_*` … `Sep_2026_*`), i.e. **September 2026 is
  the most recent month present** in the 2026 file. For ZIP 78701, the XLSX's
  `Sep_2026_Medicare_Benes`/`Sep_2026_Power_Dependent_Devices_DME` = **2072 / 49**
  — an exact match to the live REST query's `Medicare_Benes`/
  `Power_Dependent_Devices_DME` = **2072 / 49** for the same ZIP (Aug_2026 for
  78701 was 2067/52, a different pair, confirming Sep is the match and not a
  coincidence). **Conclusion: the REST FeatureServer's current snapshot is the
  September 2026 emPOWER data.**
- The REST layer itself holds only the **current/latest month's snapshot** —
  there is no month field to select older vintages from the live service. For a
  specific historical month, HHS separately publishes yearly XLSX files at
  `https://empowerprogram.hhs.gov/{YEAR}_HHSemPOWERMapHistoricalDataset.xlsx`
  (2016–2026 seen linked from `about-empowermap.html`), with a data dictionary at
  `HHSemPOWERMap_HistoricalDataset_Dictionary.xlsx`. M2 only needs the current
  snapshot, so the REST layer is sufficient; the historical XLSX files are noted
  here only as a fallback/backfill option if a later ticket needs a time series.

## Caveats

- **Small-count suppression**: cells with a true count between 1 and 10 are masked
  and reported as `11` ("any cell size found between the range of 1 and 10 is
  masked and shown as 11"). Any ZIP showing `Power_Dependent_Devices_DME == 11`
  must be treated as "≤10, exact value withheld," not a literal count of 11.
- **ZIP aggregation for non-boundary ZIPs**: some ZIPs (e.g., PO-Box-only ZIPs)
  have no geospatial boundary; HHS folds their totals into a parent ZIP
  (`Zip_Code_Recode`). A ZIP absent from the layer may simply be a child ZIP whose
  population is counted under its parent's `Zip_Code` row, not missing data.
- **`maxRecordCount` = 2000** per query — a full-state or full-county pull needs
  `resultOffset` paging (or use `f=geojson`/CSV export) if the result would
  exceed 2000 rows. Not an issue for Travis/Harris-scoped queries.
- **No per-month field on the REST layer** — only the latest snapshot is queryable
  live; historical months require the separate yearly XLSX downloads named above.
- **Denominator caveat from HHS docs**: `Medicare_Benes` covers Medicare FFS
  (Parts A&B) and Medicare Advantage (Part C) enrollees only; it excludes people
  covered only by state Medicaid, so it undercounts total electricity-dependent
  residents versus a full population figure.
- Not a browser-only dependency: this is a documented, anonymous-access ArcGIS
  REST API, verified working via plain `curl` (no auth, no browser rendering
  needed).

## Verification performed

- `curl` to `about-empowermap.html` confirmed the FeatureServer URL and the yearly
  XLSX download links.
- `curl` to the FeatureServer root and to layer `1?f=json` confirmed
  `capabilities: "Query,Extract"`, `allowAnonymousToQuery: true`, `maxRecordCount:
  2000`, and the full field list above.
- Live query against layer 1 for the 41 ZIP codes in the 78701–78759 range
  (`STATE='TX'`) returned HTTP 200 with 41 features.
- `returnCountOnly=true` confirmed exact row counts: Harris County TX = 130,
  Travis County TX = 50, all of TX = 1850 — all under the 2000-row
  `maxRecordCount`, so no pagination was actually required for these queries
  (see Endpoint section for the corrected pagination note).
- `where=STATE='TX' AND Zip_Code<>Zip_Code_Recode` returned **zero** features —
  in this layer's TX rows, `Zip_Code` and `Zip_Code_Recode` are always equal, so
  which field is the "current" ZIP vs. the "recoded/parent" ZIP could not be
  distinguished from TX data alone; use `Zip_Code` as the join key regardless
  since it is the field that matches the plain ZIP (e.g. `78701`), and treat this
  as an assumption if a state with PO-Box-only ZIPs shows a mismatch later.
- `returnDistinctValues=true` on `Zip_Code` for `STATE='TX'` returned exactly
  1850 distinct values, matching the plain row count for `STATE='TX'` — so
  **`Zip_Code` is unique within `STATE='TX'`** in this layer; `(STATE, Zip_Code)`
  (or `Zip_Code` alone, since ZIPs don't repeat across states in this dataset)
  is a safe primary/unique key candidate for `core.empower_zip`.
- Downloaded `https://empowerprogram.hhs.gov/2026_HHSemPOWERMapHistoricalDataset.xlsx`
  (12,441,529 bytes) into the **main checkout's**
  `data/raw/empower/2026_HHSemPOWERMapHistoricalDataset.xlsx` (not this worktree,
  and not `git add`-ed), with a `retrieved_at.txt` (`2026-09-26T04:05:42Z`) and
  `SHA256SUMS` (`5f1a6e38b16c0291e7cc1269ecd1bfb5d4f6e730f265e9333d465e3cb4ffe87a`)
  alongside it. This confirmed the file has sheets `State`, `County`, `Zip Code`,
  each with one column-set per month (`Jan_2026_*` … `Sep_2026_*`), and that the
  live REST snapshot's ZIP 78701 values match the XLSX's `Sep_2026_*` columns
  exactly (see Cadence section) — this is how "latest month = September 2026"
  was established, since the REST layer itself carries no month field.

## Recommendation for M2-P4

`pipelines/sources/empower.py` should hit
`{base}/1/query?where=STATE='TX'&outFields=Zip_Code,Medicare_Benes,Power_Dependent_Devices_DME&returnGeometry=false&f=json`,
paging with `resultOffset`/`resultRecordCount` past the 2000-row limit, and record
an `ops.source_manifest` row for the pulled snapshot (with retrieval timestamp,
since the REST layer has no month field of its own — the manifest's retrieved-at
time is the only record of vintage). Treat `Power_Dependent_Devices_DME == 11` as
suppressed/≤10, not literal.
