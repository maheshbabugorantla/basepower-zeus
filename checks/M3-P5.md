## Adapter

`pipelines/sources/wcad_parcels.py`, adapter name `wcad_property_data_export`.
Lean mode (whole-file-in-memory, no resumable cursor — largest file is
~140 MB/1.39M rows), matching `tcad_improvements.py`'s precedent. Batched
COPY + upsert (`BATCH_SIZE=5000`), pausing before every batch while
`pg_stat_activity` shows another backend running `refresh materialized
view`, `refresh_all_scores`, or a `copy ... from stdin` (covers a
concurrent Harris HCAD COPY).

**Single-family-homestead filter, applied BEFORE loading:** a WCAD
PropertyID is loaded only if it has a Land row with `StateCode` starting
`'A1'` (Texas's single-family-residential class code — confirmed live:
dominant land code, 214,104/305,880 rows) AND an Exemptions row with
`ExemptionTypeDescription='Homestead'` and `ExemptionStatusCode='A'`
(active). This exactly mirrors `core.mv_home_block_group`'s live gate
(read from `supabase/migrations/0102_m1_materialize.sql` before writing
any code):
```sql
where (p.imprv_state_cd like 'A1%' or p.land_state_cd like 'A1%')
  and p.hs_exempt = 'T'
```
`land_state_cd='A1'`, `hs_exempt='T'` are written only when that holds;
never `'F'` (WCAD's Exemptions table has no "no exemption" row to read a
definitive false from — absence stays null, not asserted-false).

**ID collision:** WCAD's `PropertyID` (e.g. `'63689'`) is a short,
unprefixed integer, the same shape as TCAD's `prop_id` — collision risk
confirmed real (core.parcels.prop_id is one shared text PK across
counties). Every Williamson row's `prop_id` is `'W' + PropertyID` (e.g.
`'W63689'`), consistently across `core.parcels`, `core.parcel_geoms`,
`core.parcel_improvements`. `geo_id` (TCAD's Austin-permit join key) has
no WCAD equivalent and is left null.

**`ov65_exempt` is always left null** (never `'T'`/`'F'`) — real-data-rule
decision, not an oversight: WCAD's Exemptions table conflates over-65 and
disabled-person applicants under a single "Tax Code 11.13(c) Exemption"
type (Texas Tax Code Sec. 11.13(c) grants the same extra homestead
exemption to both groups), and a separate "Disabled Person" exemption
type also exists with no way to cross-reference age. Nothing in this data
distinguishes an over-65 11.13(c) row from a disabled-but-under-65 one, so
guessing was refused. `core.mv_home_signals_v2` already reports this as
`owner_65_null_reason='exemption_data_missing'` for a null `ov65_exempt`
— no downstream code change needed.

**Improvements (yr_built/living_area):** Segment rows for a PropertyID
are grouped by `InstanceID` (one physical improvement); every
`Type` starting `'MA'` (`MA`=Main Area/1st floor, `MA2..MA8`=further
floors, `MAZ`=Mezzanine, `MAB`=Basement — confirmed live by sampling every
distinct `Segment.Type`) is a living-area floor. The "main" improvement
per PropertyID is the InstanceID with the largest total `MA*` area;
`living_area` is that sum; `yr_built` is that improvement's plain `'MA'`
segment's `ActYrBuilt`, falling back to the largest-area `MA*` segment's
`ActYrBuilt` if no plain `'MA'` exists — same fallback rule
`tcad_improvements.py` uses for TCAD's `'1ST'` code. `ActYrBuilt` of 0/blank
is null, never a literal year 0.

## The 137 TCAD-rolled homes already sitting in Williamson — no double count

`core.mv_home_signals.county_fips` is geometry-based (a spatial join
against real county boundaries, not `core.parcels.county_fips`'s own
per-adapter hardcoded value — see `0102_m1_materialize.sql`'s note on
this exact point). Before this ticket, 137 TCAD `prop_id`s (Travis-rolled,
`county_fips='48453'` in `core.parcels`) already had a centroid landing
inside Williamson county, per `core.mv_home_signals`.

Before loading, every WCAD candidate polygon was checked with
`ST_Contains` against those 137 centroids (`_tcad_williamson_overlap_prop_ids`
in `wcad_parcels.py`, using a temporary indexed `geometry` column, not
per-row WKT text reparsing — the first version of this query timed out
against the pooler's statement timeout; see "Deviations" below). **109**
WCAD candidates whose polygon contained one of those 137 TCAD centroids
were dropped (`filter_drops.on_tcad_roll=109`) and never loaded.

Post-load verification (run live, the acceptance evidence for "no home
counted in both Travis and Williamson"):
```sql
select count(*) from core.mv_home_signals hs
join core.parcel_geoms tpg on tpg.prop_id = hs.prop_id
join core.parcel_geoms wg on wg.prop_id like 'W%'
where hs.county_fips = '48491'
  and extensions.ST_Contains(wg.geom, tpg.centroid)
```
→ **0 rows.** (The other 28 of the 137 TCAD homes have no matching WCAD
footprint at all — e.g. a mismatch in exact parcel-line surveys or no
WCAD roll entry for that lot — so there was nothing for them to overlap.)

## Deviations from a clean first pass

The first backfill attempt failed: `_tcad_williamson_overlap_prop_ids`'s
original query staged candidate polygons as plain WKT `text` and called
`ST_GeomFromText` inside a correlated `EXISTS` subquery, re-parsing every
candidate's polygon text once per TCAD centroid checked (137×) with no
spatial index — it hit the pooler's `statement_timeout` and also exposed
a bug where the failure handler's own `runs.finish()` call raised
`InFailedSqlTransaction` (masking the real error) because the aborted
transaction was never rolled back first. Both are fixed in the committed
code: the overlap check now stages candidates into a real indexed
`geometry` column (GIST), and the failure handler rolls back before
recording the failure on a fresh connection. The second backfill run
succeeded cleanly (exit code 0, see counts above).
